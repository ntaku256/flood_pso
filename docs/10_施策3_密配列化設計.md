# 設計書: 施策③「{pos,state}個別Compound列挙 → 密3D numpy配列」改修

## 結論（採用アーキテクチャ）

`dem_to_blocks_enhanced` の**判定ロジックは一切触れず**、最終のボクセル化のみを変更する。具体的には、`nx×nz` 確定直後（terrain_render.py:803-806）に**1タイル分の密3D numpy配列 `arr[y,z,x]`（shape=(Y,Z,X)、dtype=uint16、0=air）を確保**し、16箇所の `blocks.append(Compound({...}))` を**薄い `BlockGrid.set(x,y,z,state)` シムへ機械的に置換**する。後勝ち（建物/橋/凡例/軒の上書き）は密配列への単純代入で自然に実現される。書き出しは (1) viewer/Minecraft 互換の Structure NBT を**ストリーミング直列化**（中間 Compound 群を生成しない）、(2) litematic を `nbt_to_litematic` の既存 `pack_litematica_bits` へ**密配列を直結**（.nbt readback を廃止）の2経路に分岐させる。これにより 8-12GB の主因である数千万個の `nbtlib.Compound`／`nbtlib.List[Int]` 生成（terrain_render 全 append サイト＋nbt_export.py:286/307）を排除する。

## 設計（密配列の具体仕様）

### 軸順 = (Y, Z, X)（`arr[y,z,x]`）

- 根拠: litematic／Structure NBT の確定 index 公式は `index = y*sx*sz + z*sx + x`（YZX, X 最速。nbt_to_litematic.py:11,96）。numpy の **C-order flatten は最終軸が最速**なので、shape を `(Y,Z,X)` にすれば `arr.reshape(-1)` がそのまま litematic の 1D YZX 配列になり、`pack_litematica_bits` へ無変換で渡せる。
- 座標規約は現状維持: `x=i_`（列／東+）、`z=j`（行／北 z=0）、`y`=高さ（terrain_render.py:943, _lonlat_to_grid_xy:290-294）。`set(x,y,z)` は `arr[y,z,x]` に書く。x↔z の取り違えは全 viewer/litematic を壊すため厳守。
- 既存 2D マップ（surf_block, 各 mask, dem_ds 等）は全て `(nz,nx)=(z,x)` なので、`set` 内の `arr[y, j, i_]` と添字順が一致し、転置ミスを起こしにくい。

### dtype = uint16、air = 0

- パレットは最大 ~80 色（block_palette.py）。`PALETTE_KEYS` は **air=0 を保証**（block_palette.py:139-140）。0 初期化＝未書き込み＝air がそのまま成立し、「置かないセルは air」規約（nbt_to_litematic.py:94）を密配列で自然再現。
- uint16 は将来の色追加に対する余裕。**現状の <256 色なら uint8 でメモリ半減**も可（後述試算）。負値は不要なので符号なしが素直。

### palette: block_id → index

- `state` は `PALETTE_INDEX[name]`（= `PALETTE_KEYS` の list 添字、nbt_export.block_id と同一。nbt_export.py:60-61）。密配列のセル値＝この index を直接格納するため、`BlockGrid.set` の引数は現状 append が既に算出している `state`(int) をそのまま受ける。
- 書き出し時のパレットは現状同様 **`PALETTE_LIST_KEYS` 全体を固定 palette** として使う（出現色のみの再構築はしない）。これで litematic の `bits=max(2,(len(palette)-1).bit_length())`（~7bit）と Structure NBT の palette index が現状と完全一致し、**byte一致を狙える**。

### max_y / nx / nz の確定タイミング

- `nx, nz` は downsample factor 確定直後（terrain_render.py:803-806）に確定 → **X,Z 寸法は配列確保時点で確定**。
- `max_y` は建物(:1182)・樹木(:1281)・橋(:1292)・避難所(:1316) を生成し終えるまで確定しない。対応策（推奨は (a)）:
  - **(a) y_cap=501 で確保し最後にトリム**: 既存の y ガード `0<=y<=500`（:581,:1011,:1213）と完全一致。`set` 内で範囲外を捨て、`grid.max_y` を更新。最後に `arr = arr[:max_y+1]` して返り size `[nx, max_y+1, nz]`（terrain_render.py:1378）を現状維持。低リスク。ピークは 501 層分（後述試算で許容内）。
  - (b) 事前パスで Y を算出してから確保: メモリ最小だが追加コード大。最適化として将来検討。

### 後勝ち（legend 層含む）は単純代入で自然実現

- 同一 `(x,y,z)` への複数書き込みは `arr[y,z,x] = state` の上書きで**最後の代入が勝つ**。append 順を保てば現状の last-wins（nbt_to_litematic.py:97）と一致。
- 凡例 full=True 3層（y=0,2,4。最後に emit。:1343）、橋（最後。:1283）、建物（陸地表の後）、軒（:1177）の上書きはすべて「set を呼ぶ順序」を現状の append 順のまま保てば再現。**散布(scatter)ベクトル化はしない**（numpy の重複 index 代入は評価順未定義のリスク。JSON risks 参照）。逐次 set でループ順＝後勝ち順を厳守。

## 移行戦略（最重要）: 薄い BlockGrid シム

### 推奨案: BlockGrid シムで append を機械的置換

```python
class BlockGrid:
    def __init__(self, nx, nz, y_cap=501, dtype=np.uint16):
        self.nx, self.nz = nx, nz
        self.arr = np.zeros((y_cap, nz, nx), dtype=dtype)  # (Y,Z,X), 0=air
        self.max_y = 0
    def set(self, x, y, z, state):
        if 0 <= x < self.nx and 0 <= z < self.nz and 0 <= y < self.arr.shape[0]:
            self.arr[y, z, x] = state
            if y > self.max_y:
                self.max_y = y
```

置換は機械的:

```python
# Before (16サイト共通形)
blocks.append(nbtlib.Compound({'pos': nbtlib.List[nbtlib.Int]([Int(i_),Int(fy),Int(j)]),
                               'state': nbtlib.Int(st)}))
# After
grid.set(i_, fy, j, st)
```

- 対象 append サイト: terrain_render.py:589-592(橋 put), 953-956, 960-963, 966-969, 972-975, 993-996, 999-1002, 1012-1015, 1139-1142, 1168-1171, 1177-1181(軒), 1216-1218(樹木), 1307-1310, 1312-1315, 1324-1327(土台層), 1343-1345(凡例)。**判定・高さ計算ループはそのまま**、Compound 生成行だけ差し替える。
- **境界クランプを `set` に集約**: 軒(:1177)・樹木近傍(:1212)・橋 put(:580-585) の範囲外/隣接書き込みは `set` 内の範囲チェックで一律ガード（現状の個別ガードと等価。IndexError 防止）。
- **土台層(:1322-1327)・凡例(:1335-1376) のベクトル化（任意）**: `arr[_found_y, :, :] = deepslate_idx`、`arr[layer_y, :, :] = glass_idx` の全面代入で nz×nx の Python 二重ループを消せる（メモリ・速度の追加利得。後勝ち順序は「凡例は最後に代入」を守れば不変）。これは置換と独立に適用可能。

#### add_bridge_blocks の二層セマンティクス維持

- 橋内部は `seen` 集合で**先勝ち**（:586-588）、橋 vs 他カテゴリは**後勝ち**（橋を最後に処理）。`put()` を「`(x,y,z) in seen` なら return、それ以外は `seen.add` + `grid.set`」に変更すれば、橋内部の先勝ちと、橋が最後に呼ばれることによる対他カテゴリ後勝ちの両方が保たれる。grid 側の無条件上書きと矛盾しない。

### 代替案: 全面書き換え（ベクトル化散布）

各カテゴリを `argwhere` のセル集合＋縦範囲から numpy の slice 代入で一括 scatter。

| 観点 | BlockGrid シム（推奨） | 全面書き換え |
|---|---|---|
| 差分量 | append 16行のみ。判定ロジック温存 | 大。各カテゴリのループを書き換え |
| 後勝ち再現 | 逐次代入で自明に保証 | 重複 index 代入の評価順が numpy 未定義 → 要 `np.maximum.at` 等で別途保証 |
| 数値一致検証 | 容易（既存 .nbt と差分） | 散布順の検証が重く回帰リスク大 |
| 速度 | append より速い（Python オブジェクト生成消滅）。ループは残る | 最速だが可変高柱の scatter 化が複雑 |
| リスク | 低 | 中〜高 |

**結論: シムを採用**。速度より「コード忠実・低リスク・数値一致」を優先。土台層/凡例のような自明な全面層だけは部分的にベクトル化。

## 書き出し（2経路）

### 経路1: 密配列 → Structure NBT（viewer/Minecraft 互換維持）

- 現状 `write_nbt_structure`（nbt_export.py:277-313）は `nbtlib.List[Compound](blocks)` 再ラップ(:286)＋nbtlib 直列化(:307) がピーク主因。**密配列をそのまま nbtlib.List へ展開すると施策③の効果が消える**（JSON risks 明記）。
- 対策: **密配列専用のストリーミング NBT ライタを追加**。`ys,zs,xs = np.nonzero(arr)`（air 以外）で座標を一括取得し、gzip ストリームへ blocks タグを逐次バイト書き込み（nbtlib の Compound ツリーを作らない）。root スキーマ（DataVersion=Int(4671), author, size=List[Int]([nx,ny,nz]), palette=List[Compound], blocks=List[Compound{pos,state}], 空 entities, flood_pso_meta）と gzip 保存は厳守（nbt_export.py:289-310, must_preserve）。
- blocks の**並び順は append 順 → nonzero 順(Y,Z,X 昇順)に変わる**が、密配列で既に last-wins 解決済みのため**重複 pos が消え**、意味は等価（readback も litematic も順序非依存）。viewer は pos/state を読むだけなので互換。
- `flood_pso_meta`（build_meta_compound, nbt_export.py:240-274,298-305）はストリーミングライタでも root 直下に同型で書く。

### 経路2: 密配列 → litematic（既存密実装を生成側へ前倒し）

- `nbt_to_litematic` は既に `.nbt` を readback → 密YZX配列 → `pack_litematica_bits`（nbt_to_litematic.py:44-65,92-98）。**密配列は terrain_render 側で既に YZX で持っている**ため、`structure_dense_to_litematic(arr, PALETTE_LIST_KEYS, size, out)` を新設して `pack_litematica_bits(arr.reshape(-1), bits)` に直結。
- これで **litematic 生成では `.nbt` 中間生成と nbt_preview の per-block Python ループ(nbt_preview.py:99)を完全に回避**できる。

### .nbt 中間を廃せるか

- viewer/Minecraft 取り込みの成果物が `.nbt` のため**完全廃止は不可**。ただし「litematic を作るための .nbt readback」は廃止可。
- 推奨運用: make_nbt_hd は 1パスで「経路1（.nbt ストリーミング書き出し）」と「経路2（密配列→litematic 直結）」を**同じ密配列から両方生成**。`--no-litematic`（既存, make_nbt_hd.py:524-526）に加え、litematic のみ欲しい場合の `--no-nbt` を足せば .nbt 生成自体もスキップ可能（任意）。

## メモリ試算

### 1タイル（例 nx=1196, max_y+1=95, nz=1426）

- **密 uint16**: 1196 × 95 × 1426 × 2B ≈ **324 MB**（air 含む全ボクセル、トリム後）。uint8 なら ≈ **162 MB**。
- **現状 Compound**: 非air ボクセル ≒ X·Z·平均柱高。平均柱高 ~20 と仮定で 1196·1426·20 ≈ 3.4×10⁷ 個。各 `Compound`(dict)＋`List[Int]`(3要素)＋Int×4 で実測 ~200-300B/個 → **6.8〜10 GB**。さらに nbt_export.py:286 の再ラップで二重保持。→ 観測の 8-12GB と整合。
- y_cap=501 で確保しトリム前のピークは 1196×501×1426×2B ≈ **1.7 GB**（トリム後 324MB）。Compound 方式比で大幅減。ピークを嫌うなら事前パス (b) で 324MB に抑制可。

### huge_5m 全域

- 全域を単一密配列にすると例: 5000×200×5000×2B ≈ **10 GB**（JSON risk: 密でも天井に当たる）。
- 回避: **施策③は必ずタイル単位で密配列を確保**（make_nbt_hd の `--tiles` は 1タイル=1 export_to_nbt 呼び出し。make_nbt_hd.py:333-358,445,488）。タイルごとに ~324MB を確保→書き出し→解放を繰り返すため、**全域サイズに依らずピークはタイル1枚分**に固定。これが省メモリの前提（must_preserve: per-call/per-file 単位維持）。
- 1タイルでも Y が極端に大きい場合の将来策: arnis 流の section(16³)分割＋Uniform(全air)圧縮（common.rs:84-141,282-364）。現行タイル幅では不要。

## 不変条件の維持

- **flood_pso_meta**: ストリーミングライタで root 直下に同型埋め込み（nbt_export.py:240-274,298-305）。
- **タイル分割**: per-tile 密配列、1タイル=1ファイル。export_to_nbt の per-call 構造不変（make_nbt_hd.py:445,488）。
- **可変高さ柱**: 高さ計算（_under_depth minimum_filter :981-986, y_sea_surface/floor, y_flood_top, 建物 top_y, 樹高, 橋）と縦ループは温存し、append のみ set 化 → 可変高を完全保持。固定高化しない。
- **海 NaN / マスク判定**: ベクトル化済み判定（sea_mask/land_mask/surf_block 等）は無改修。dense 既定 0=air で未充填＝air を維持。
- **座標規約・後勝ち・air省略・palette index・DataVersion=4671・grass/leaves Properties**: 上記設計で全て保持。
- **施策①②との両立**: ①②（判定側のベクトル化等）は本改修（append→set の出力段置換）と独立。判定ロジックを温存するため衝突せず、同じ密配列に対して後段で適用される最適化とも両立。

## 段階的な実装手順（各ステップ単体で生成テスト可能）

1. **BlockGrid シム追加**（terrain_render.py）。まだ append は残し、`set` を `blocks.append` と並行呼び出しにして dense を埋める（dead path）。生成は現状通り通る。
2. **検証フック追加**: dense から `np.nonzero` で {pos,state} を再構成し、既存 blocks list と last-wins 解決後に一致するか assert（オフライン比較）。1タイルで一致確認。
3. **append を set へ置換**（16サイト）＋ y_cap/トリム導入。返り値を `(arr, size)` へ変更。橋 put の seen 二層を維持。経路は依然 .nbt（dense→nonzero→既存 write_nbt_structure）でテスト。ブロック種別個数・bbox が手順2と一致するか確認。
4. **ストリーミング NBT ライタ追加**（nbt_export 側）。dense から直接 gzip 書き出し。出力 .nbt を nbt_preview/litematic で readback し、手順3の .nbt とボクセル等価（last-wins後）を確認。ここで nbt_export.py:286/307 のピーク解消。
5. **litematic 直結**（structure_dense_to_litematic 新設）。dense→pack_litematica_bits。手順4の .nbt 経由 litematic とバイト一致を確認 → .nbt readback 経路を litematic 生成から外す。
6. **土台層/凡例の全面代入ベクトル化**（任意）。後勝ち順序維持で個数一致を再確認。
7. legacy `dem_to_blocks`（nbt_export.py:179-219）も同方式へ（必要なら）。

## 検証計画

- **ボクセル等価（最重要）**: 同一タイル・同一パラメータで、改修前パイプラインの litematic 内部 dense `D_old`（nbt_to_litematic.py:92-97 で .nbt から構築）と、改修後の生成側 dense `D_new` を比較し `np.array_equal(D_old, D_new)`。last-wins と座標規約を一括検証。
- **ブロック種別ごとの個数**: dense の `np.bincount(arr.reshape(-1))` を改修前後で比較（air を含む全 index）。
- **bbox**: 各 state について nonzero の min/max(x,y,z) 一致。
- **size 一致**: 返り `[nx, max_y+1, nz]` が改修前後で一致。
- **litematic バイト一致**: `D_old==D_new` かつ固定 palette のため `.litematic` を **byte-for-byte** 比較（pack_litematica_bits 決定論）。
- **.nbt 等価**: 改修前 .nbt は重複 pos を含むため、両者を「(x,y,z)→state の last-wins dict」へ正規化して比較（生 byte 比較は順序差で不一致になるので不採用）。
- **メモリ実測**: 1タイルで RSS ピークを改修前後で計測し GB→数百MB を確認。

- **dtype**: 現状 <256 色なので uint8（162MB）採用か、将来余裕の uint16（324MB）か。
- **移行方式**: BlockGrid シム（推奨・低リスク）でよいか、全面ベクトル化書き換えまで踏み込むか。
- **max_y 確定**: y_cap=501 確保→トリム（ピーク1.7GB/タイル、低リスク）でよいか、事前パスで Y 算出（324MB だが追加コード）まで行うか。
