**性能はサブPCの方が上**。メインPCの優位は「LiDAR が 10図郭ある」ことだけ。

### 重要: `world-full` は現状どちらでも回せない

Makefile の `world-full` は **18図郭**を要求するが、
**8図郭（`06RC701` `06RC702` `06RC711` `06RC713` `06RC803` `06RC811` `06RC813` `06RC911`）が
どちらのマシンにも存在しない**（txt / npz とも 0 ファイル、ホーム全体を検索して確認）。

→ 御坊全域を再生成するには**和歌山県オープンデータから 8図郭を再取得**する必要がある。
それまでは 10図郭以下の範囲での生成に限られる。

**原則**: コードの変更と単体検証はサブPCで完結させる。生成対象がサブPCに無い図郭を含むときだけメインPCを使う。

## 1. Python 環境

### uv を使うこと（`python3 -m venv` は失敗する）

このマシンには `python3-venv`（`ensurepip`）が入っておらず sudo も使えないため、標準の venv 作成は失敗する:

```
The virtual environment was not created successfully because ensurepip is not
available.  On Debian/Ubuntu systems, you need to install the python3-venv package
```

そのため **uv を既定の手順とする**:

```bash
cd flood_pso
uv venv .venv --python 3.10
uv pip install --python .venv/bin/python -r requirements.txt
```

**既存の `.venv` には pip が入っていない**。`.venv/bin/pip` は存在しないので、パッケージ追加も uv 経由で行うこと:

```bash
uv pip install --python .venv/bin/python <package>
```

実行は `.venv/bin/python` を直接叩く（`Makefile` の `PY` 変数もそうなっている）。

### 検証済みの組み合わせ

`requirements.txt` のピンは **Python 3.10.12（サブPC）で検証した値**。
2026-08-05 に uv でクリーン環境を作り、全12パッケージの import 通過を実測確認済み。

**メインPC は Python 3.12.3 で、より新しい版が入っている**
（numpy 2.4.4 / scipy 1.17.1 / pandas 3.0.3 / rasterio 1.5.0 など）。
この構成のまま **全 src モジュールの import・`tools/` の compile・実データ `make crop`（14.6秒）が通る**ことを
2026-08-05 に実測確認したので、**メインPC側で無理にピンへ合わせて downgrade しないこと**。
（pandas 2.x → 3.0 のような major 差があるため、downgrade の方が壊れるリスクが高い）

ピンはあくまで「サブPC で再現性を担保するための既知の良い組み合わせ」と考える。

> `opencv-python` は `requirements.txt` に載っていたが `cv2` は `src/` 内で一度も import されていないため削除した。
> 逆に**実際に使っている `rasterio` と `shapely` が抜けていた**ので追加した。

## 2. 必要な外部データ

コードだけでは生成できない。以下は別途配置が要る。

### 2.1 LiDAR 点群（和歌山県 3次元点群オープンデータ）

**生 txt は転送しないこと。npz キャッシュだけでよい。**

| 形式 | サイズ | 備考 |
|---|---|---|
| 生 txt | **1図郭あたり約860MB**（grd 134MB + org 724MB） | 18図郭で約15GB |
| npz キャッシュ | 南部4図郭で **574MB** | 実際の生成はこちらを読む |

`data_cache/wakayama_lidar/` に配置する。命名規則:

- `{図郭コード}_grd.grid{解像度}m_pp.npz` — 地表DEM（ground、地物除去済）
- `{図郭コード}_org.grid{解像度}m_{exc3|keep3}.npz` — DSM（建物実高さ。`exc3`=樹木クラス除外 / `keep3`=保持）
- `{図郭A}_grd+{図郭B}_grd+...grid{解像度}m_pp.npz` — 複数図郭の結合 mosaic

解像度は `--scale` に対応（`scale 1.5` → `0.666667m`、`scale 2.0` → `0.5m`）。

**サブPCにあるのは南部4図郭**: `06RC904` / `06RC913` / `06SC002` / `06SC011`
結合 mosaic の範囲: lat 33.820086〜33.847364 / lon 135.157140〜135.200608（約3×4km、dem shape (4556, 6030)）
crop の既定中心 lat 33.8337 / lon 135.1789 はこの mosaic の中心。

**メインPCにあるのは10図郭**: 上記4つ + `06RC703` `06RC704` `06RC801` `06RC802` `06RC804` `06RC902`
（`data_cache/wakayama_lidar` 全62ファイル・11GB。txt と npz の両方）

**どちらにも無い8図郭**: `06RC701` `06RC702` `06RC711` `06RC713` `06RC803` `06RC811` `06RC813` `06RC911`
→ 御坊全域を再生成するなら**和歌山県オープンデータから再取得が必須**。

#### npz の命名がマシン間で違う

- サブPC: `06RC904_grd.grid0.666667m_pp.npz`（**`_pp` 付き** = DEM後処理を通した版）
- メインPC: `06RC802_grd.grid0.666667m.npz`（**`_pp` 無し** = 後処理導入前のキャッシュ、62ファイル全部）

メインPCのキャッシュは 2026-06-26 の DEM後処理導入（施策①）より前に作られたもの。
そのままコピーしても命名が違うのでキャッシュヒットしない点に注意。

出典表記は必須: 「和歌山県 3次元点群データ（航空レーザ測量）を加工して作成」

### 2.2 基盤地図情報 FG-GML（国土地理院）

`../kennkyuu20260114/地形データ/` 配下（Makefile:21-22 が相対パスで直参照している）。

| ディレクトリ | サイズ | 内容 |
|---|---|---|
| `FG-GML-503561-ALL-20251001/` | 79MB | 北側メッシュ。BldA(建物28MB) / RdEdg(道路12MB) / WA・WStrA(水域) / RailCL(鉄道224KB) |
| `FG-GML-503551-ALL-20260101/` | 19MB | 南側メッシュ。同上（BldA 6.4MB） |

御坊全域は lat 33.8333 を跨ぐので**両メッシュの union が要る**。

#### git-LFS の実体取得を忘れないこと（必ず踏む罠）

`kennkyuu20260114` は git-LFS 管理。実体を引いていないと XML がポインタファイル（4KB）のままで、
生成が以下のエラーで落ちる:

```
lxml.etree.XMLSyntaxError: Start tag expected, '<' not found, line 1, column 1
```

中身を見ると `version https://git-lfs.github.com/spec/v1` で始まっている。対処:

```bash
cd ~/web-app/kennkyuu20260114     # メインPCのパス
export PATH=$HOME/.local/bin:$PATH   # git-lfs はユーザローカル導入
git lfs pull --include "地形データ/FG-GML-503561-ALL-20251001/*.xml,地形データ/FG-GML-503551-ALL-20260101/*.xml"
```

LFS 管理は 269 ファイルあるが、生成に要るのは上記2ディレクトリだけなので **`--include` で絞る**こと
（2026-08-05 にメインPCで実行、9秒で完了）。
実体が入ったかは `head -c 5 <xml>` が `<` で始まるかで判定できる。

## 3. 転送するもの / しないもの

### 転送する

- リポジトリ本体（コード）
- `data_cache/wakayama_lidar/*.npz`（**txt は不要**）
- `data_cache/osm/*.json`
- `../kennkyuu20260114/地形データ/FG-GML-*`

### 転送しない（再生成可能）

- `results/anvil/`（11GB）— Anvil ワールド出力
- `results/nbt/`（9.3GB）— 中間 structure NBT
- `results/world/` `results/inspect/` `results/data_preview/gobo_full/`
- `data_cache/wakayama_lidar/*.txt`（3.9GB）— npz があれば不要
- `.venv/`（uv で作り直す）

> リポジトリには `.gitignore` に該当するのに tracked のままのファイルが **46件・107MB** ある
> （`results/nbt/hd/*.nbt` `*.litematic` が36件）。clone を軽くするなら `git rm --cached` で追跡から外す余地がある。
> ただし履歴には残るので、`git clone --depth 1` を使うのが手っ取り早い。

## 4. 生成コマンドの使い分け

```bash
# 高速反復（数十秒）。橋・トンネルのコード修正 → 確認 のループ用
make crop                      # 既定: 中心 lat 33.8337 / lon 135.1789, 400m角
make crop CLAT=.. CLON=.. W=.. # 中心・サイズ上書き

# 南部4図郭でのオプション検証（十数分）
make world-test

# 御坊全域18図郭の本番生成（5.29時間 / 2.2GB）
#   ※ 8図郭が欠落しているため現状どちらのマシンでも回せない（§0 参照）
make world-full
make world-full LEGEND=--legend-layer   # 地下にLayer C可視化層を入れる場合
```

メインPCで crop を回すときは、そちらにある図郭を明示する:

```bash
ssh moriken@desktop-74slhtm-1
cd ~/web-app/flood_pso
make crop CLAT=33.88096 CLON=135.16762 W=400 \
     GRD4=data_cache/wakayama_lidar/06RC802_grd.txt \
     ORG4=data_cache/wakayama_lidar/06RC802_org.txt \
     BRIDGES_S=data_cache/osm/gobo_bridges_geom.json
# 2026-08-05 実測 14.6秒（Python 3.12・新しめのパッケージのまま完走）
```

> `make world-test` は元々 `06RC701/702` を参照していて**入力欠落で即死していた**。
> issue#3 で残存する南部4図郭へターゲットを切り替えた。

### gobo_zeniki_v3 について

プレイに使っていた `gobo_zeniki_v3` は Makefile に存在しない。実体は
`make world-full LEGEND=--legend-layer` を **commit 138b4ee** で回した出力（`results/anvil/gobo_zeniki_v2`）を
Windows の `saves/` へ手コピーして改名したもの（中間NBTの `flood_pso_meta` に `git_revision` が刻印されていて確定）。

**橋バグ修正 bb20921 より前のビルド**なので、基準にするなら現行の `results/anvil/gobo_zeniki_v2`（bridgefix版）の方が新しい。
