## Phase 5：ネイティブ GPU ビューア（外部リポジトリ）

NBT を Web で見ようとするとブラウザがクラッシュするため、Rust + Bevy 0.15 でネイティブビューアを別リポジトリとして実装。

- リポジトリ: <https://github.com/ntaku256/flood_pso_viewer>
- ローカル: `/home/moriken/web-app/flood_pso_viewer/`
- 仕様詳細: `flood_pso_viewer/docs/00_開発記録.md`

主要機能：
- `flood_pso_meta` コンパウンドを右パネルに展開（method / K / D / loss / IoU / dh_map ヒートマップ）
- Minecraft Creative 風 FlyCam（WASD + Tab マウス capture + Space/Shift 上下）と Orbit カメラを F で切替
- `--no-water` または V キーで **浸水前 ↔ 浸水後** をワンクリック比較
- WSL2 の Mesa Zink 経由でホスト GPU（AMD Radeon 等）が掴めるようバックエンド優先順位を自動判定
- 自作 `VoxelMaterial`（埋め込み WGSL）で Bevy 標準 PBR の WSL 互換性問題を回避
- XZ チャンク分割 greedy meshing（rayon 並列）で frustum culling を効かせる

参考実装：
- `web-app/schematic-renderer/mesh_builder_wasm/src/lib.rs` — greedy meshing アルゴリズム
- `web-app/redstone-lib/packages/viewer` — 軽量 isometric ビューア構成

## Phase 6：地形レンダ改善（Tellus 風 enhanced モード）

`flood_pso_viewer` で見たときの地形「精度の低さ」3 点（海岸線・海の表現が雑、緑斜面の階段化、地表ブロックの不自然さ）を、`web-app/Tellus/`（Earth-scale Minecraft Fabric mod）の worldgen 実装を参考に改善。
詳細は `docs/07_地形レンダ改善.md`。

主要変更：
- 新ファイル `src/terrain_render.py` — cliff-aware smoothing、海岸距離→段階水深、slope/convexity ベースの地表ブロック分類、陸/海で v_exag 分離
- `nbt_export.py:export_to_nbt(terrain_quality="enhanced"|"legacy", ...)` — 切替フラグ追加、enhanced を default に
- `make_nbt.py` / `make_nbt_hd.py` に `--quality {enhanced,legacy}` / `--sea-level` 追加
- legacy 出力はファイル名に `_legacy` サフィックス、enhanced（無印）と並存可能
- 研究本体（PSO/CCPSO2 校正）には影響しない（`simulate_flood_hd` 出力をそのまま使う、ブロック化のレンダ層だけ変更）

## Phase 8：歩行可能な高精細ワールド（2026-06-17）

目的：研究軸（PSO/CCPSO2 校正）とは別の **Layer C / 防災教育コンテンツ軸**。
「マイクラで実際に歩き回れる」精度（1 ブロックあたりの m を小さく）を目指す。

ボトルネック整理：
1. 元データが GSI 5m（DEM5A/5B）。真の 5m 以下は **DEM1A(1m LiDAR)** 入手か補間が必要。
   `dem_parser.py` は GML ヘッダから grid 寸法を読む汎用実装なので **DEM1A はコード変更ゼロで読める**
   （`FLOOD_PSO_DEM_DIR` を DEM1A ディレクトリへ向けるだけ）。DEM1A は FGD ダウンロード
   サービス（要ログイン）からのみ。和歌山の整備可否は 2025-03 拡大リストに明記なし→要確認。
2. 1m/block 自体は **enhanced 経路が既に bilinear アップサンプル**（`nbt_export.py` の
   `if h_res < h_res_dem*0.95: nd_zoom`）。5m DEM でも 1m/block は出る（滑らかだが真の 1m 詳細は無い）。
3. 歩ける町には建物・道路が必須。OSM 経路（`--use-osm`）はあったが、**FG-GML ローカルベクタ
   （BldA/RdEdg、API 不要・高精度）が未配線**だった。

実装：
- `src/fgd_vector.py` 新設。BldA(建物ポリゴン)・RdEdg(道路ライン)を逐次パースし、
  `tellus_data.fetch_osm_buildings_roads` と同じ dict 形に変換（bbox クリップ・LFS 実体化要）。
  → 下流のラスタライズ（`terrain_render.build_osm_masks`）と配置（`dem_to_blocks_enhanced`）を
    一切変更せず再利用。
- `nbt_export.export_to_nbt(use_fgd, fgd_bld_xml, fgd_rdedg_xml)` 追加。OSM と併用時は mask を union。
- `make_nbt_hd.py`：`--use-fgd` と歩行用 preset `gobo_walk_1km/2km`（1m/block, **v_exag=1 真スケール**,
  市街地中心 33.8875,135.1515）を追加。出力名サフィックス `_fgd`。

実測（gobo_walk_1km, 500m×500m, gt）：建物 815 棟・道路 96 本を配置（building mask 85,863 / road 61,668 セル）、
598×15×498 ブロック、5.1MB、31s。トップダウンで日高川・建物群・道路網が視認でき「町」になった。

### 真の 1m 地形：和歌山県 LiDAR（2026-06-17 続き）

GSI DEM1A は御坊で未整備の公算大（2025-03 拡大に和歌山なし）。代わりに **和歌山県が独自公開する
航空レーザ測量点群オープンデータ**（2023-03〜, 県域65%, 御坊含む）を採用。
- ポータル `https://wakayamaken.geocloud.jp/mp/22`（手動DL）。図郭 `06RC802` を取得（grd 133MB / org 388MB）。
- 形式：CSV `id, easting, northing, Z`（**平面直角座標系VI = EPSG:6674, JGD2011**, CRLF）。
  grd=グラウンド(地形), org=オリジナル(DSM)。06RC802 は lat[33.874,33.888] lon[135.157,135.178] の 2km×1.5km。
- 新ファイル `src/wakayama_pcd.py`：点群 370万点 → pyproj で系VI→WGS84 → 1m 緯度経度グリッドに bincount 集約
  → NaN 隙間を最近傍埋め → `dem_parser` 互換 dict。.npz キャッシュ（2 回目以降 2 秒）。要 `pip install pyproj pandas`。
- `make_nbt_hd.py --wakayama-grd <grd.txt>`：DEM ソースをこれに切替、中心はタイル被覆へ自動設定。
  h_res=1m かつ DEM が 1m なので **アップサンプル無し＝ネイティブ真の 1m**。
- 検証：gobo_walk_1km gt lidar → 500×57×498（起伏が 57 ブロックに反映）, 191 棟, 5.9MB, 32s。

未了：
- LiDAR タイルは市街地東側中心（密集市街地は西端寄り）。複数図郭の連結や中心調整は要なら対応。
- ビン化で 1m グリッドの ~40% が隙間→最近傍埋め（実効 ~1.4m）。res 調整 or org(DSM) 併用は将来課題。
- 建物高さは現状 `building_height_m` 一律（per-type 高さは `fgd_vector` が tags に持つが配置側は未使用）。

## 主要結果（要約）

| K | D | PSO_loss (depth MAE) | CCPSO2_loss | 優位 |
|---|---|---|---|---|
| 4 | 17 | 0.0007 ± 0.0005 | 0.0145 ± 0.0063 | **PSO** |
| 8 | 65 | 0.0135 ± 0.0027 | 0.0649 ± 0.0138 | **PSO** |
| 16 | 257 | 0.1629 ± 0.0422 | **0.1148 ± 0.0163** | **CCPSO2** |

→ **D=257（高次元）で CCPSO2 が標準PSO を逆転。分散も小さく安定**。研究仮説（CCPSO2 は高次元問題に有効）の実証エビデンス。
