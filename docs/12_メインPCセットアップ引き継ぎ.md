## 2. 環境構築

### 2.1 WSL2

`flood_pso` は Linux 前提（Anvil 書き出し・点群処理・Overpass 取得）。Windows ネイティブでは動かない。

```powershell
wsl --install -d Ubuntu
```

Tailscale も入れておくと他マシンから SSH で入れて便利
（サブPCから作業を手伝ってもらう場合に必要。`wsl-<hostname>` としてノードが増える）。

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
sudo apt install -y openssh-server && sudo systemctl enable --now ssh
```

### 2.2 リポジトリ

```bash
mkdir -p ~/web-app && cd ~/web-app
git clone https://github.com/ntaku256/flood_pso.git
git clone https://github.com/ntaku256/kennkyuu20260114.git   # FGD データ置き場（LFS）
cd flood_pso && git checkout 3-partial-test-generation
```

**ディレクトリ構成の前提**: `Makefile` は FGD を `../kennkyuu20260114/地形データ/...` と
**相対パスで直参照**している。2つのリポジトリは必ず同じ親ディレクトリに置くこと。

### 2.3 Python 環境

```bash
# uv を使う（python3-venv/ensurepip が無い環境では標準 venv が失敗する）
curl -LsSf https://astral.sh/uv/install.sh | sh
cd ~/web-app/flood_pso
uv venv .venv --python 3.10
uv pip install --python .venv/bin/python -r requirements.txt
```

`requirements.txt` のピンは Python 3.10 で検証した値。
**Python 3.12 でも、より新しい版のまま動くことを実測確認済み**なので、
3.12 環境なら無理にピンへ downgrade しないこと（pandas 2.x→3.0 の major 差があり downgrade の方が危険）。

### 2.4 FGD（基盤地図情報）— LFS の罠に注意

```bash
cd ~/web-app/kennkyuu20260114
git lfs install
git lfs pull --include "地形データ/FG-GML-503561-ALL-20251001/*.xml,地形データ/FG-GML-503551-ALL-20260101/*.xml"
```

**必ず `--include` で絞ること。** LFS 管理は 269 ファイルあり全部引くと無駄に重い。
上記2ディレクトリだけで9秒。

実体が入ったかの確認:

```bash
head -c 5 地形データ/FG-GML-503561-ALL-20251001/FG-GML-503561-RailCL-20251001-0001.xml
# '<' で始まれば OK。'versi'（= version https://git-lfs...）ならポインタのまま
```

ポインタのまま生成すると以下で落ちる:

```
lxml.etree.XMLSyntaxError: Start tag expected, '<' not found, line 1, column 1
```

御坊全域は lat 33.8333 を跨ぐので **503561（北）と 503551（南）の両メッシュが要る**。

### 2.5 OSM

```bash
cd ~/web-app/flood_pso
make osm-fetch                       # 橋/トンネル/電線/駐車場を Overpass から取得
make osm-check                       # 欠落・0件・壊れが無いか確認
```

`make world-full` は `osm-check` を前提条件にしているので、揃っていないと python 到達前に止まる。
持っていないフィーチャは明示的に無効化する: `make world-full POWER= PARKING=`

## 3. LiDAR 点群データ（本題）

### 3.1 必要なもの

図郭コード単位。1図郭につき2ファイル:

- `{code}_grd.txt` — 地表（建物・樹木を除去した ground）。67〜162MB
- `{code}_org.txt` — 全点（DSM）。5列目がクラス値（class3=植生）。386MB〜1.2GB

配置先は `data_cache/wakayama_lidar/`。

`Makefile` の `world-full` は **18図郭**を要求する:

```
06RC701 06RC702 06RC703 06RC704 06RC711 06RC713 06RC801 06RC802 06RC803
06RC804 06RC811 06RC813 06RC902 06RC904 06RC911 06RC913 06SC002 06SC011
```

### 3.2 現在どこに何があるか（2026-08-05 実測）

| 図郭 | サブPC(Taku128) | 学校PC(moriken) |
|---|---|---|
| 06RC703 704 801 802 804 902 | — | **あり** |
| 06RC904 913 06SC002 011 | あり | **あり** |
| 06RC701 702 711 713 803 811 813 911 | **無し** | **無し** |

- 学校PC が上位互換（10図郭・生txt 10GB）。共通分はファイルサイズも一致
- **8図郭はどちらにも無い** → 再取得が必要

### 3.3 入手方法

配信元は和歌山県の GeoCloud:

- 公式ページ: https://www.pref.wakayama.lg.jp/prefg/012100/d00213012.html
- 配信システム: https://wakayamaken.geocloud.jp/mp/22

2023-03-01 公開、県土の約65%が対象。データ種別は3つ（表層 / 地表 / グリッド）。
測地系は **JGD2011 平面直角座標系 第VI系 EPSG:6674**。

> **注意**: 単純な HTTP GET は **403 Forbidden** で弾かれる（2026-08-05 確認）。
> 対話型 Web GIS なのでブラウザ操作が要る可能性が高い。
> 静岡県には自動DLアダプタ（`tizucraft/adapters/shizuoka_tiles.py`、S3 の ListObjectsV2 を列挙）が
> あるが、**和歌山には同等の実装が無い**。ここを自動化できると再現性が大きく上がる。

**出典表記は必須**: 「和歌山県 3次元点群データ（航空レーザ測量）を加工して作成」

### 3.4 学校PCから貰う方が速い場合

10図郭ぶんは学校PCに既にある。再ダウンロードするより貰った方が確実:

```bash
# 生 txt（10GB。Tailscale DERP 中継 2.6MB/s なら約65分）
rsync -av --progress moriken@desktop-74slhtm-1:~/web-app/flood_pso/data_cache/wakayama_lidar/*.txt \
      data_cache/wakayama_lidar/

# npz キャッシュだけなら 474MB・約3分（生成済み・すぐ使える）
rsync -av --progress \
      moriken@desktop-74slhtm-1:'~/web-app/flood_pso/data_cache/wakayama_lidar/*0.666667m*_pp.npz' \
      moriken@desktop-74slhtm-1:'~/web-app/flood_pso/data_cache/wakayama_lidar/*0.666667m*_exc3.npz' \
      moriken@desktop-74slhtm-1:'~/web-app/flood_pso/data_cache/wakayama_lidar/*0.666667m*_keep3.npz' \
      data_cache/wakayama_lidar/
```

#### npz キャッシュの命名規則（重要）

```
{code}_grd.grid{解像度:g}m_pp.npz          ← 地表。_pp = DEM後処理あり
{code}_org.grid{解像度:g}m_exc3.npz        ← DSM（植生class3 を除外）
{code}_org.grid{解像度:g}m_keep3.npz       ← DSM（植生class3 のみ）
{codeA}_grd+{codeB}_grd....npz             ← 複数図郭の結合 mosaic
```

- `_pp` が付くのは **grd だけ**。`org` はクラスフィルタ付きなので postprocess 対象外
  （`src/wakayama_pcd.py:97` — `postprocess = postprocess_enabled() and not (exclude_classes or keep_classes)`）
- 解像度は `--scale` に対応。`scale 1.5` → `0.666667m`（本番）、`scale 2.0` → `0.5m`
- **txt が無くても npz があれば生成は動く**（ローダがキャッシュ優先）。
  ただし別解像度が欲しくなったら txt が要る
- 学校PCの古い npz には `_pp` が付いていないものがある（DEM後処理導入 2026-06-26 より前のキャッシュ）。
  現行コードは `_pp` を探すのでキャッシュミスして txt から作り直す。
  2026-08-05 に学校PC側で `_pp` 版を生成済み（9件・258秒）

## 4. 動作確認

```bash
cd ~/web-app/flood_pso

# 1) 高速反復（数十秒）。まずこれが通れば環境は正しい
make crop CLAT=<中心緯度> CLON=<中心経度> W=400 \
     GRD4=data_cache/wakayama_lidar/<code>_grd.txt \
     ORG4=data_cache/wakayama_lidar/<code>_org.txt \
     BRIDGES_S=data_cache/osm/gobo_bridges_geom.json

# 2) 断面で目視確認（Minecraft を起動せずに橋・トンネルを検証できる）
.venv/bin/python tools/nbt_section.py results/anvil/gobo_crop \
     --way <OSM way id> --geom-json data_cache/osm/gobo_bridges_geom.json \
     --center <lat>,<lon> --size 400x400 --margin 40 -o /tmp/section.png

# 3) 本番（18図郭が揃ってから。5.29時間 / 出力2.2GB）
make osm-check && make world-full
```

図郭の緯度経度範囲は npz から読める:

```bash
.venv/bin/python -c "
import numpy as np
d = np.load('data_cache/wakayama_lidar/<code>_grd.grid0.666667m_pp.npz')
print(f\"lat[{float(d['lat_min']):.5f},{float(d['lat_max']):.5f}] lon[{float(d['lon_min']):.5f},{float(d['lon_max']):.5f}] {d['dem'].shape}\")
"
```

## 5. 既知の残件（issue #3）

メインPCで本番を回すときに効きうるもの:

- **`world-full` の実地検証が未了** — 2026-08-05 の修正はすべて crop / 合成データでの検証。
  18図郭の本番で通していない
- crop DEM から生成した世界は、全域 mosaic から生成した世界と**地表ディザの素材が食い違う**
  （世界座標基準に DEM 配列インデックスを渡しているため、切り出すと原点がずれる）
- crop + `--reuse-inundation` の洪水キャッシュ名が DEM 形状を含まず**誤再利用しうる**
- 送電線/トンネルの頂点が全域DEMの外（`search_cells=8` 超）だとアンカーが付かずフォールバックする
- 断面ツールの `--thick>1` 警告が集計値比較なので、細い空洞の消失を見逃しうる
